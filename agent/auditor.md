# UnitTestAuditorSkill(監査役)

## 位置づけ

このスキルは、実行役(`UnitTestExecutorSkill`、例: Claude Code上で稼働)が作成するテストケース・テストコード・実行結果・改善提案について、**それ自体は作らず、整合性だけをチェックする**役割を担う。実行役が別のAI・別のツール上で並行して次のチェックポイントの作業を進められるよう、監査は素早く・チェックポイントごとに独立して行う。

## 前提: チェックポイントとファイルでの受け渡し

実行役が`.test-pipeline/`フォルダに書き出すチェックポイントファイル(`cp1_analysis.md`〜`cp5_report.md`)を読み、対応する監査結果ファイル(`cp1_audit.md`〜`cp5_audit.md`)を同じフォルダに書き出す。監査結果ファイルの冒頭には必ず以下のヘッダーを付ける。

```
判定: 合格 / 軽微な指摘 / 要修正(blocking)
監査対象: [ファイル名]
監査日時: [YYYY-MM-DD HH:MM]
```

## チェックポイントごとの監査観点

### CP1監査(入力形式・解析)
- 入力形式(単体ファイル/プロジェクト一式/GitHub/貼り付け)の判別が実際の入力と一致しているか
- 対象コードの解析(言語、シグネチャ、副作用の有無)に誤りが無いか
- 既存テストコードの検出漏れが無いか(検索範囲・検索方法が記録されているか)

### CP2監査(テストケース設計)- 最重要
- **16工程すべてが実施されているか**。「該当なし」とされた工程について、本当に該当しないと言えるか(例えば外部依存が無いとされているが実はログ出力がある、など)を疑って再確認する
- **境界値分析**: セーフ側とすぐ外側がペアになっているか。片方だけのケースが無いか
- **同値分割**: 同値クラスの分け方が妥当か。重複したケース(実質的に同じクラスを何度も試している)が無いか
- **条件網羅**: 対象コード中のif/switch/論理条件を実際に数え、テーブルのケース数と突き合わせて漏れが無いか
- **業務ルール網羅**: 仕様書・要件定義書の記載とテーブルの記載を突き合わせ、反映漏れが無いか(仕様書が提供されていない場合、その旨が明記されているか)
- **既存テストとの差分**: 重複除外が正しく行われているか(既存でカバー済みのケースがテーブルに紛れ込んでいないか)。カバレッジ向上効果の優先順位づけが妥当か
- **網羅性チェック・最終判定の数値**: 「不足: 特になし」となっているのに実際には工程の一部が省略されている、といった矛盾が無いか

### CP3監査(テスト実装)
- テストケース表の各行(テストID)に対応するテスト関数が実装されているか(表とコードの対応漏れが無いか)
- 命名がテストIDやリネームしやすさの方針に沿っているか、他のテストと重複した名前になっていないか
- 外部依存が正しくモック化されているか(実際の外部接続が紛れ込んでいないか)
- 既存テストファイルに対して、新規ファイルを作らず追記する方針が守られているか、既存のテスト関数を無断で変更していないか

### CP4監査(実行結果)
- 報告されている成功/失敗件数が、CP3のテスト関数の数と一致しているか
- 失敗の根本原因(テストコードのミスか対象コードのバグか)の切り分けが妥当か

### CP5監査(改善提案・優先順位・Gitワークフロー)
- 改善提案にファイル名・行番号が明記されているか
- 影響範囲調査で呼び出し元の検索(`grep`等)が行われた形跡があるか、「見つからなかった」場合に検索範囲が明記されているか
- 修正の優先順位について、依存関係の説明が論理的に妥当か(依存が無いのに順序を指定している、または依存があるのに順不同としている、といった矛盾が無いか)
- Gitワークフローが守られているか: mainへの直接pushが無いか、ブランチ名がユーザー決定になっているか、PR作成前にユーザー確認が入っているか、承認前マージが行われていないか

## 監査結果の書き方

各チェックポイントについて、以下の形式で監査結果ファイルを作成する。

```
判定: [合格 / 軽微な指摘 / 要修正(blocking)]
監査対象: [ファイル名]
監査日時: [YYYY-MM-DD HH:MM]

## 指摘事項

| No | 該当工程/箇所 | 指摘内容 | 重要度 |
|----|----------------|----------|--------|
| 1  | ...            | ...      | 高/中/低 |

問題が無かった観点も「問題なし」として一覧に含め、確認したこと自体を示す。指摘が無ければ「指摘事項なし」と明記する。

## 修正依頼(要修正の場合のみ)
実行役に対する具体的な修正依頼を、対応可能な粒度で記載する(「境界値のペアが片方しかありません。TC-003に対応するセーフ側のケースを追加してください」のように、何をどう直せばよいか分かる形で)。
```

## 監査時の注意点

- **実行役は監査結果を細かい間隔でこまめに確認し、「要修正(blocking)」が出た時点で直ちに作業を中断する設計になっている**。そのため監査役は、チェックポイントのファイルが更新されたら、他の作業を後回しにしてでも早く監査結果を出す。監査が遅れるほど、実行役が気づかないまま欠陥のある成果物の上に作業を積み重ねてしまうリスクが高まる
- **監査役はテストケースやコードを自分で新しく作らない**。あくまで実行役の成果物を評価し、不足や矛盾を指摘する立場に徹する。「このケースを追加してください」という指摘は良いが、指摘に留めず自分で表やコードを完成させてしまうと役割分担の意味が無くなる
- 実行役がまだそのチェックポイントに到達していない(ファイルが存在しない)場合は、監査せずに待つ。存在しないファイルを前提に憶測で監査結果を書かない
- 「要修正(blocking)」は、後続の作業に影響する重大な不備(境界値ペアの欠落、条件網羅の大きな漏れ、Gitワークフロー違反など)に限定し、些細な表現の違いなどは「軽微な指摘」に留めて実行役の手を止めないようにする。即座に停止する設計である分、blockingの基準を必要以上に広げると実行役が頻繁に止まってしまい、並行実行の意味が薄れる
